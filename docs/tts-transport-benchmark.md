# TTS Streaming Transport Benchmark

Date: 2026-08-13

## Result

Use `grpc.aio` for TTS-pool's low-latency streaming interface. Each synthesis
uses an independent unary-request, server-streaming RPC. One long-lived channel
can carry concurrent synthesis streams.

The initial protocol microbenchmark found equivalent first-audio latency for
raw HTTP/2 and gRPC at one to four concurrent streams. A second comparison used
a production-shaped ASGI HTTP/2 stack. gRPC was equal at concurrency one and
about 6-7 ms earlier at concurrency two and four over Wi-Fi.

Raw HTTP/2 was faster in the artificial 500- and 1,000-stream burst. That load
does not represent model execution. Both transports completed all logical
streams.

The production choice also limits the refactor: `grpc.aio` can run beside the
existing Uvicorn server in the same TTS-pool process and share the existing
engine and fair scheduler.

## Test Environment

- Client: `dc1`, `192.168.178.202`
- Server: `dc2`, `192.168.178.203`
- Network: both hosts connected by Wi-Fi through the same router
- TTS model: `openbmb/VoxCPM2` through `nanovllm_voxcpm`
- TTS-pool service revision on dc2: `5924acc`
- Benchmark base revision on dc1: `663ecfb`
- Python: 3.12
- gRPC: `grpcio` 1.83.0
- HTTP/2: `h2` 4.4.1
- Production-shaped HTTP/2: Hypercorn with HTTPX

The existing TTS-pool stayed active on port 8020. The benchmark server used
temporary processes on separate ports:

- raw HTTP/2: 18020
- `grpc.aio`: 18021
- ASGI HTTP/2: 18022

The GPU was at 0% utilization before and after the measurements. The benchmark
did not start or stop the loaded services.

## Network Baseline

A 200-packet ping immediately before the main Wi-Fi run measured:

| Metric | Result |
| --- | ---: |
| Packet loss | 0% |
| Minimum RTT | 2.713 ms |
| Mean RTT | 3.612 ms |
| Maximum RTT | 19.362 ms |
| RTT deviation | 1.307 ms |

The maximum RTT shows why sub-millisecond transport differences on this route
are not meaningful. Protocol order alternated on every repeat to distribute
short Wi-Fi disturbances across both candidates.

## Workload

Both servers consumed the same synthetic async chunk iterator. Its timing and
output matched the measured warm NanoVLLM request shape:

- 65 ms before the first chunk;
- 32 audio chunks;
- 15,360 PCM bytes per chunk;
- 28 ms between chunks;
- 491,520 output bytes;
- about 0.94 seconds from request admission through the last chunk.

The 491,520 bytes represent 10.24 seconds of 24 kHz, mono, signed 16-bit PCM.
The reference case uploaded 246,044 binary bytes, matching the WAV generated by
the existing scheduler benchmark.

One warm connection carried all concurrent streams for a protocol. Each
concurrency and repeat finished before the other protocol ran. The first
protocol alternated between repeats.

## Existing API Baseline

One live request of each shape went through the existing JSON and complete-WAV
API from dc1 to dc2:

| Request | Client wall time | TTS-pool wall time | Time outside pool synthesis |
| --- | ---: | ---: | ---: |
| No reference | 1,395.7 ms | 935.4 ms | 460.3 ms |
| Paired reference | 1,535.0 ms | 948.9 ms | 586.1 ms |

The current path uploads reference audio as base64 JSON and downloads the
complete WAV as base64 JSON. The comparison does not isolate every part of the
460-586 ms difference. It does show that complete-response delivery is a much
larger latency target than the small difference between the streaming
transports.

## Warm Wi-Fi Results

Time to first audio includes request transmission, 65 ms of simulated backend
work, transport delivery, and client scheduling.

### Without Reference Audio

| Concurrent streams | Raw HTTP/2 median | Raw HTTP/2 p95 | gRPC median | gRPC p95 |
| ---: | ---: | ---: | ---: | ---: |
| 1 | 79.2 ms | 82.8 ms | 78.9 ms | 85.6 ms |
| 2 | 85.6 ms | 104.7 ms | 82.1 ms | 91.1 ms |
| 4 | 92.9 ms | 118.7 ms | 93.3 ms | 117.7 ms |

The single HTTP/2 maximum at concurrency two was 228.8 ms. The corresponding
gRPC maximum was 92.4 ms. No repeated pattern established that this was a
protocol effect rather than a Wi-Fi outlier.

### With a 246,044-Byte Reference

| Concurrent streams | Raw HTTP/2 median | Raw HTTP/2 p95 | gRPC median | gRPC p95 |
| ---: | ---: | ---: | ---: | ---: |
| 1 | 192.1 ms | 203.1 ms | 192.2 ms | 203.2 ms |
| 2 | 274.9 ms | 318.0 ms | 268.2 ms | 316.4 ms |
| 4 | 483.9 ms | 628.7 ms | 485.6 ms | 626.5 ms |

The reference upload dominates the difference between this table and the
no-reference table. Protocol framing does not materially change it.

## Loopback Results

Loopback removes Wi-Fi from the first-audio path.

### Without Reference Audio

| Concurrent streams | Raw HTTP/2 median | gRPC median | Difference |
| ---: | ---: | ---: | ---: |
| 1 | 67.3 ms | 67.9 ms | 0.6 ms |
| 2 | 67.7 ms | 68.1 ms | 0.4 ms |
| 4 | 68.4 ms | 68.6 ms | 0.2 ms |

### With a 246,044-Byte Reference

| Concurrent streams | Raw HTTP/2 median | gRPC median | Difference |
| ---: | ---: | ---: | ---: |
| 1 | 69.4 ms | 68.7 ms | 0.7 ms gRPC |
| 2 | 71.2 ms | 69.5 ms | 1.7 ms gRPC |
| 4 | 71.8 ms | 70.0 ms | 1.8 ms gRPC |

Raw HTTP/2 has a sub-millisecond advantage for a tiny request. gRPC has a small
advantage while accepting the reference body. Neither result is large enough
to drive the production choice.

## Production-Shaped HTTP/2 Comparison

The raw HTTP/2 benchmark isolates protocol overhead but omits an ASGI server
and HTTP client. A second comparison therefore used Hypercorn, an ASGI
streaming response, and one multiplexed HTTPX connection. It used the same
synthetic chunk source as the gRPC server.

### Loopback

| Concurrent streams | ASGI HTTP/2 median | gRPC median | gRPC advantage |
| ---: | ---: | ---: | ---: |
| 1 | 69.3 ms | 67.9 ms | 1.4 ms |
| 2 | 70.8 ms | 68.0 ms | 2.8 ms |
| 4 | 72.4 ms | 68.6 ms | 3.8 ms |

### Wi-Fi

| Concurrent streams | ASGI HTTP/2 median | gRPC median | gRPC advantage |
| ---: | ---: | ---: | ---: |
| 1 | 79.4 ms | 79.5 ms | none |
| 2 | 88.1 ms | 80.7 ms | 7.4 ms |
| 4 | 96.7 ms | 90.4 ms | 6.3 ms |

The Wi-Fi run used ten repeats per concurrency. One gRPC request at concurrency
one had a 5.119-second total-duration outlier; its first-audio maximum was 140
ms. A longer ASGI HTTP/2 run ended with a server-disconnected transport error
while both benchmark server processes remained alive. The host also had an
unrelated SSH-tunnel restart storm, so that failure cannot be assigned to the
HTTP/2 stack from this run alone.

## Cold Connections

Fifty new Wi-Fi connections per protocol used one audio chunk after the 65 ms
backend delay:

| Protocol | Median first audio | p95 first audio |
| --- | ---: | ---: |
| Raw HTTP/2 | 80.2 ms | 86.3 ms |
| gRPC | 78.2 ms | 84.7 ms |

Production uses a long-lived channel. This check only confirms that a reconnect
does not create a large gRPC penalty.

## Slow Consumer Isolation

Four loopback streams each carried 7.5 MiB. One consumer delayed every received
chunk by 10 ms. The other three consumed without an added delay.

| Protocol | Normal streams median | Normal streams maximum | Slow stream median |
| --- | ---: | ---: | ---: |
| Raw HTTP/2 | 699.7 ms | 704.3 ms | 5,662.1 ms |
| gRPC | 694.6 ms | 716.0 ms | 5,449.0 ms |

The slow stream did not hold up the other streams for either protocol.

## Cancellation

The client cancelled after the first chunk. Twenty-five batches of four
streams ran for each protocol over Wi-Fi. A 100 ms pause between batches let
already-written network data drain before the next batch.

The client cancelled all 200 streams. Normal requests immediately after the
test completed for both protocols. No client-visible stream state accumulated.
This does not prove that cancelling a future NanoVLLM async generator releases
an active sequence promptly.

## Logical-Stream Scale

Both protocols completed every stream over one warm connection:

| Concurrent streams | Raw HTTP/2 p95 | gRPC p95 |
| ---: | ---: | ---: |
| 500 | 104.3 ms | 112.4 ms |
| 1,000 | 164.2 ms | 238.7 ms |

Each stream returned one 256-byte chunk with no backend delay. This is a
connection-state stress test, not a model-capacity target. Raw HTTP/2 handles
the burst faster. gRPC still completes 1,000 streams without a second channel.

## Decision Rationale

Use `grpc.aio` because:

- it matches or improves first-audio latency at one to four concurrent streams;
- it carries reference and output audio as binary messages;
- one channel multiplexes at least 1,000 logical streams in the prototype;
- flow control, deadlines, and cancellation are part of the RPC transport;
- it provides a typed streaming contract without custom frame parsing;
- it can be added beside the existing FastAPI/Uvicorn server.

The production implementation should start one gRPC server beside the existing
HTTP API in the same process. Both interfaces must use the same engine,
scheduler, and loaded model instances.

## Limits

- The cross-host measurements use one Wi-Fi network.
- The main matrix models measured NanoVLLM timing but does not stream live
  NanoVLLM output.
- Both comparisons used isolated temporary benchmark processes rather than the
  production TTS-pool service.
- The cancellation result covers transport state, not active GPU-sequence
  release.
- The test measures delivery mechanics, not speech quality.
